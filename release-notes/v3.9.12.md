# snapgentV3 V3.9.12

This release **locks each session to one VS Code workspace** and adds **one session per chat tab, each on its own project**. With several VS Code windows open, switching to another window no longer moves a running session to that other project, and two chat tabs (for example DeepSeek on `bpr` and another tab on `psak414`) can work on two different projects at the same time. `bridge.py` is changed (it forwards the calling tab id), so **both `bridge.exe` and `vscode_mcp.exe` need to be rebuilt** (see Upgrade).

## One session per chat tab

- **Project picker before Start.** With the VS Code target selected and a chat ready, the bar shows a new pill listing every project folder the open VS Code windows contain (focused window first, marked "focused"). Pick one; the status line shows `Ready · VS Code · <folder>`. Start then locks exactly that folder for this tab.
- **Per-tab pins.** The extension stamps every tool call with its tab id; the bridge forwards it and the MCP server keeps one pinned workspace per tab. Tab 1 on `bpr` and tab 2 on `psak414` never see each other's files, and switching VS Code windows affects neither.
- **Persistent pins.** The per-tab registry survives an MCP server restart (`.snapgent_sessions.json` next to `vscode_mcp.exe`, or `ZS_WORKSPACE_LOCK`'s folder). A pin whose folder was deleted is ignored, never blocks the tools.
- **Manual override.** The MCP settings popup's **Lock / Unlock** buttons now operate on this tab's session pin.
- New MCP tool `list_vscode_windows` returns the open project folders; `get_workspace_info` reports `workspace_source` `session` (per-tab pin), `lock` (global), `app` (picked folder) or `vscode-window`, plus `workspace_session`.
- Without a picker choice, Start locks the folder of the window focused at that moment - the single-tab behaviour from before still works unchanged.

### Fixed
- **Session followed the focused VS Code window.** The VS Code MCP server picked its workspace from VS Code's own "last active window" state, so every time you focused a different open VS Code project, the next tool call silently read and edited that other project's files. A running session now keeps the workspace it started with, no matter which VS Code window is focused.

### Added
- **`lock_workspace` MCP tool.** Called with no arguments it pins the folder VS Code currently has focused; with a `path` it pins that folder. Only a folder VS Code currently has open (as reported by `list_vscode_windows`) or the app-picked workspace can be locked, so a model-driven call can never move the workspace boundary to an arbitrary directory on disk. While a lock is in place, every workspace tool operates on the locked folder. With a tab id (injected by the bridge) the pin is per-tab.
- **`unlock_workspace` MCP tool.** Removes the pin - the calling tab's own pin when called from a chat tab, the global lock otherwise.
- **Sessions lock automatically.** Every new session start (VS Code target) pins the workspace chosen in the picker, or the one active at that moment, so a stale pin from a previous session can never hijack a new one. A toast confirms which project was locked ("Workspace locked: <name>").
- **Workspace row in the MCP settings popup** (Switch AI menu → gear icon). It shows the workspace name, full path and lock state, with **Lock to this workspace** / **Unlock** buttons for a manual override (per-tab).
- **The status bar names the project.** The bar's status line reads `Active · 31 tools · VS Code · <project-folder>` instead of a bare "VS Code", with a 🔒 glyph when the session is pinned. Hovering shows the full folder path and the lock state. Before Start, the Ready line names the workspace that will be used.
- **Chat sidebar titles name the project.** The bootstrap message now opens with `Session: work on the project "<name>" …`, so the AI site titles the conversation after the locked project instead of "List vscode commands" (sites derive the title from the first message and never re-title).
- `get_workspace_info` now reports `workspace_locked` (true/false), `workspace_source` (`session`, `lock`, `app` or `vscode-window`) and `workspace_session`.

### Changed
- The workspace status probe uses `get_workspace_info` instead of `list_dir` (same failure cases, plus the lock state).
- Resolution order inside the MCP server: the calling tab's session pin → the standalone app's picked folder (`ZS_WORKSPACE`) → the global lock file (`.snapgent_workspace.lock` next to `vscode_mcp.exe`, or `ZS_WORKSPACE_LOCK`) → the focused VS Code window. A pin pointing at a deleted folder is ignored, never blocks the tools.
- Extension and Snapgent App versions bumped to **3.9.12** / **0.1.2**.

### Upgrade
Rebuild **both** `bridge.exe` (from `bridge.py`, changed) and `vscode_mcp.exe` (from `vscode_mcp.py`, changed - `vscode_mcp.spec` is unchanged, but the exe needs a rebuild to pick up the new tools) with PyInstaller, then reload the extension at `chrome://extensions` (or `edge://extensions`) and refresh open chat tabs (F5) so the popup shows `ext v3.9.12`. Restart the bridge so the new MCP server is used. Open two chats, pick a project in each bar's project pill, and Start each - they run independently.
